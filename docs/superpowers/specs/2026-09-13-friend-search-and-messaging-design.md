# Friend search, handles and private messages

Approved 2026-09-13. Players find each other by a unique `@handle`, add them through the
friend flow that already exists, and send private messages that are stored, so a message
to someone offline is waiting when they next log in.

Friendships already exist and are persisted (`game_friendships`, `server/friends.mjs`).
Private messages already exist as the `dm` chat channel with a conversation strip
(`src/dm.ts`). This spec adds the three things missing: a findable identity, search, and
durable delivery.

## Why today's DMs cannot do this

`server/index.mjs` looks the target up in `currentRoom.players` and refuses unless their
socket is open, replying "That player is no longer in the city." A DM therefore needs both
players online and in the same room, and nothing is kept. Display names are also not
unique — no constraint exists — so "search by username" has nothing to match against.

## Identity: handles

`player_handles`, one row per account.

```
player_handles = { user_id (pk, references auth.users on delete cascade), handle, created_at }
```

Rules:

- 3 to 18 characters, lowercase `a-z`, `0-9` and `_` only.
- Unique on `lower(handle)`, so `@Yusuf` and `@yusuf` cannot coexist.
- Reserved, refused as an exact match: `mod`, `moderator`, `gm`, `support`, `system`.
- Reserved, refused as a prefix, since these are the ones worth impersonating:
  `admin`, `staff`, `official`, `lepakmamak`. So `admin_yusuf` is refused but `modi` is not.
- **Permanent once claimed.** A changeable handle frees the old one for impersonation.
- Search matches handles only, never display names.

### Claiming

The first login after release shows a single screen that cannot be dismissed. It is
pre-filled from the display name, lowercased and stripped of disallowed characters. If that
is taken, reserved or under 3 characters, the lowest free numeric suffix from 2 is appended,
so `yusuf` becomes `yusuf2`. Availability is checked live as the player types. A claim that
loses a race to the unique index returns `taken` with a fresh suggestion.

## Messages

`game_messages`.

```
game_messages = {
  id uuid, sender_user_id, recipient_user_id,
  body text (1..500, stored raw), client_id text,
  sent_at timestamptz, read_at timestamptz null,
  pair text generated always as (least(sender,recipient) || ':' || greatest(sender,recipient))
}
unique (sender_user_id, client_id)
index (pair, sent_at desc)            -- one conversation, both directions
index (recipient_user_id, read_at)    -- unread counts at login
```

- 500 characters, matching the Wall.
- Unread is `read_at is null`. There is no separate counter to drift.
- `client_id` is generated by the sender. A retry after a lost connection reuses it, and
  the unique constraint means it is stored once.
- **The body is stored raw and filtered when shown.** Chat history stores filtered text, but
  a report needs the real words: censoring an insult to asterisks destroys the evidence.

## Blocks

`player_blocks = { blocker_user_id, blocked_user_id, created_at }`, primary key on the pair.

## Reports

`player_reports` gains `dm` in its `surface` check constraint, and a new
`evidence jsonb not null default '[]'` column holding the reported messages. `note` is
limited to 300 characters and `witnesses` means who was in earshot, so neither fits.
Reporting a conversation means a moderator reads those messages. Report evidence is never
run through `filterChat`.

## Account deletion

`OWNED_ROWS` in `server/account.mjs` gains:

```
['player_handles', 'user_id'],
['game_messages', 'sender_user_id'],
['game_messages', 'recipient_user_id'],
['player_blocks', 'blocker_user_id'],
['player_blocks', 'blocked_user_id'],
```

Deleting an account removes the messages it sent from other players' inboxes. No scheduled
retention otherwise: messages live until an account is deleted.

## Server

Following `server/friends.mjs`: every action is **HTTP with the player's bearer token**,
and anonymous users are rejected. The socket is used only to nudge a recipient, the way
friends already push `friends-updated`.

`server/handles.mjs` claims, looks up and searches handles. `server/messages.mjs` sends,
pages a conversation, marks it read, returns unread counts, and holds blocks.

| request | response |
| --- | --- |
| `POST /handles/claim {handle}` | `{handle}` or `{error: taken\|invalid\|reserved, suggestion}` |
| `GET /handles/check?h=` | `{available}` |
| `GET /players/search?q=` | `{results: [{userId, handle, name, online, relation}]}` |
| `POST /messages {to, body, clientId}` | `{message}` |
| `GET /messages/:userId?before=` | `{messages, more}` — 30 per page |
| `POST /messages/:userId/read` | `{}` |
| `GET /messages/unread` | `{threads: [{userId, handle, name, unread, lastAt}]}` |
| `POST /blocks {userId}` / `DELETE /blocks/:userId` | `{}` |

Socket, server to client: `dm-new {message}` to the recipient if online in any room, and
`handle-required` on welcome for an account with no handle.

Search is a case-insensitive prefix match, at most 20 results. `relation` is `none`,
`pending` or `friend`. Adding a friend calls the **existing** request flow unchanged.

### Who can be messaged

**Any account with a handle.** Messaging does not require a friendship. Block and report are
the protection, so both are one tap from inside a conversation.

### The send path

Every send passes these gates, in this order, in one place:

1. **Ban and mute, by its own check.** Mutes are enforced by the socket's `MUTED` set in
   `server/index.mjs`, which never sees an HTTP request, so a PM would otherwise bypass them
   entirely. This copies the Wall's own check in `server/wall.mjs`: `moderation.status()`,
   refusing banned then muted accounts.
2. **Werewolf and Lukis lockout.** The sender's room is found through `playerForUser`, and
   the existing "Geng dan DM ditutup masa main" rule applies. A sender who is not in the
   city at all is in no live game, so this gate passes.
3. **Block.** If the recipient has blocked the sender, the reply is a generic
   "You can't message this player", which neither fakes delivery nor reveals the block.
4. **Rate limit**, per sender account: at most 20 messages a minute in total, and at most
   5 to any one recipient in ten seconds. Over the limit the reply is 429 with
   `retryAfter`, so the client can say "Slow down" and when to try again.

**Fails closed.** If the moderation lookup errors, the send is refused with 503. Joining the
city fails open because failing closed would lock out everyone on a blip; the Wall fails
closed because that costs one refused post. A PM is the Wall's case.

Then the message is written, and only then pushed through `playerForUser`. A push that fails
because the socket closed is harmless: the message is already stored.

### Guests

Guests keep today's in-room DMs, unchanged.

### Dev has no database

Dev runs with no `SUPABASE_*`, so accounts, friends and the Wall are inert there today.
When no Supabase is configured, one in-memory adapter stands in for handles, messages,
blocks **and friendships**, and each guest is given a stand-in account ID for the session.
On dev, a guest holding a stand-in ID is treated as an account for this feature: it claims a
handle and uses the inbox. Its in-room DMs are unaffected. Production stays strictly
account-only; the stand-in is never issued when Supabase is configured. The adapter resets when the server restarts.

The stores sit behind one interface. **A single contract test runs against both** the
Supabase store and the in-memory store, so dev cannot quietly diverge from production.

## Client

- **Claim screen** on first login after release, as above.
- **Search** in the friends panel (`src/friends.ts`), above the existing list. Each result
  shows initial, handle, display name and online state, with **Message** and a second
  button reading **Add friend**, **Pending** or **Friends**.
- **Conversations** open in the existing strip (`src/dm.ts`), which already shows a chip per
  conversation with an unread count. The last 30 messages load; older ones page in as the
  player scrolls up.
- **Offline recipient:** "They'll see this when they're back online." shows once per
  conversation, under the first message sent while that person is offline.
- **Login:** conversations with unread messages appear straight away as chips with counts,
  from `GET /messages/unread`. Opening one marks it read.
- **Block** and **Report** in the conversation header. Report opens the existing report
  dialog with the `dm` surface and attaches recent messages.
- **Lost connection:** the draft is kept with a retry, reusing its `client_id`.

## Rollout

The migration is applied to production **before** the realtime server deploys. The server
would otherwise answer 503 on every send — the same hazard already recorded for the Wall.
The client must not ship ahead of the server: `deploy:realtime` deploys `main`, so merge
first and deploy both.

## Testing

Server specs, which import `server/*.mjs` directly:

- Handle rules: length, charset, case-insensitive uniqueness, reserved names, permanence,
  the claim race.
- Search returns handles only, at most 20, with the correct `relation`.
- A message to an online recipient in **another room** is pushed; to an offline one it is
  counted unread at their next login.
- Each gate refuses: banned, muted, Werewolf or Lukis live, blocked, rate limited.
- The moderation lookup failing refuses the send with 503.
- A retry with the same `client_id` is stored once.
- Report evidence is stored unfiltered.
- Deleting an account clears all three tables and the sent messages.
- The contract test, against both stores.

Browser: claim a handle, search, message an offline friend, relog as the friend and see the
unread chip, block, report.

## Deliberately not built

- **Read receipts.** The ask is that the recipient sees messages when they return, not that
  the sender learns when they were read. Receipts also tell people when you have looked.
- **Changing a handle.**
- **Message requests from non-friends.** Any handle can be messaged directly.
- **Scheduled retention.**
- **Discoverability controls.** Every account with a handle is searchable.
- **Group conversations.** One to one only.

## Known risk, accepted

LepakMamak appeals to children, through the Upin & Ipin village and Legoland. Private,
stored messages that any stranger can send to any handle are the channel grooming runs
through. Child-safety reports are out of scope for the moderation console and are an
escalation to the owner, not a filter change. Open messaging was chosen with this stated.
